01 · FUNDAMENTAÇÃO TEÓRICA

A Importância da Estratégia de Testes

Por que Automatizar Testes?

  • Detecção Precoce de Bugs: Reduz o custo financeiro de correções em fases avançadas.
  • Prevenção de Regressões: Garante que novas funcionalidades não quebrem funcionalidades legadas.
  • Documentação Viva: Os cenários de teste documentam o comportamento real da aplicação.

Conceitos Essenciais de Isolamento

  • Unidade de Código: O menor bloco executável isolado (classe ou método).
  • Test Doubles (Mocks/Stubs): Subtitutos controlados para dependências externas (bancos de dados, APIs, serviços).
  • Verificação de Interação: Testar não apenas o retorno, mas quantas vezes e como as dependências foram chamadas.
🎙️ O que falar: "Para entender as ferramentas, precisamos relembrar a base dos testes unitários. O objetivo é isolar a regra de negócio. Para isso, utilizamos objetos dublês, conhecidos como Mocks, evitando que dependências como banco de dados interfiram no teste."

02 · VISÃO DE ARQUITETURA

Diferenças Estruturais de Design

Spock Framework

Ecossistema Completo: Funciona como Test Runner, motor de asserções e biblioteca de Mocks ao mesmo tempo.

Meta-programação (Groovy): Permite sintaxe DSL elegante, eliminando código boilerplate e deixando os métodos com nomes em texto livre.

JUnit Platform: A partir da versão 2.x, roda nativamente no ecossistema JUnit 5.

JMockit

Toolkit de Mocking Especializado: Não executa os testes sozinho; necessita de um runner como JUnit 4/5 ou TestNG.

Manipulação de Bytecode: Utiliza a API `java.lang.instrument` para redefinir classes em tempo de execução via Java Agent.

Isolamento Profundo: Capaz de simular métodos privados, estáticos, construtores e classes `final` sem alterar a arquitetura.

🎙️ O que falar: "A grande diferença técnica está aqui: o Spock é um ecossistema completo baseado em Groovy que atua como Runner e Asserção. Já o JMockit é uma biblioteca que usa manipulação de bytecode para alterar o comportamento de classes Java em memória."

03 · SPOCK FRAMEWORK

Sintaxe BDD e Estrutura Semântica

Cada teste no Spock é chamado de Feature Method dentro de uma Specification:

Blocos Principais

  • given: / setup: Configuração inicial de fixtures e mocks.
  • when: Execução do estímulo ou ação a ser testada.
  • then: Validação de condições e verificação de interações.
  • expect: Combina estímulo e validação em uma única expressão rápida.

Recursos Avançados

  • where: Tabelas de dados para parametrizar testes (Data-Driven).
  • cleanup: Executado sempre ao final para fechar recursos ou conexões.
  • Mocks embutidos: Sintaxe nativa usando Mock(), Stub() e Spy() sem bibliotecas externas.
🎙️ O que falar: "O Spock utiliza blocos explícitos para definir as etapas do teste. Em vez de comentários informais, o código possui labels estruturados como given, when e then, forçando uma excelente organização semântica."

04 · CÓDIGO SPOCK

Exemplo Prático: BDD + Data-Driven Testing

import spock.lang.Specification

class DescontoServicoSpec extends Specification {

    def "deve calcular desconto de acordo com o perfil do cliente"() {
        given: "o serviço de cálculo de desconto"
        def calculadora = new CalculadoraDesconto()

        expect: "que o valor do desconto seja calculado corretamente"
        calculadora.calcular(valorBase, perfil) == descontoEsperado

        where: "tabela de cenários de teste parametrizados"
        valorBase | perfil       || descontoEsperado
        100.0     | 'VIP'        || 20.0
        100.0     | 'REGULAR'    || 5.0
        50.0      | 'NOVO'       || 0.0
    }
}

Destaque Técnico: O bloco where: gera múltiplos testes independentes em tempo de compilação, permitindo testar bordas e variações de dados em uma única especificação limpa.

🎙️ O que falar: "Neste exemplo em Spock, observamos a tabela de dados no bloco 'where'. Cada linha representa um caso de teste completo executado de forma independente pelo relatório da plataforma."

05 · JMOCKIT TOOLKIT

O Ciclo Record-Replay-Verify

O JMockit impõe uma separação rígida de fases baseada no padrão formal de testes:

Fases do Teste

  • 1. Record Phase: Dentro do bloco new Expectations(), grava-se quais métodos serão invocados, argumentos aceitos e os retornos/exceções forçados.
  • 2. Replay Phase: Chamada do método real sob teste. Mocks interceptam as chamadas gravadas.
  • 3. Verify Phase: Dentro de new Verifications(), confirma-se ordem, número de execuções ou limites de chamadas.

Anotações de Injeção

  • @Mocked: Simula totalmente a classe ou interface fornecida.
  • @Injectable: Simula apenas a instância específica injetada no teste.
  • @Tested: Cria automaticamente a instância da classe sob teste, injetando os mocks declarados.
🎙️ O que falar: "No JMockit, temos três passos rigorosos. No Record, definimos as Expectations. No Replay, executamos o código real. No Verify, checamos se as chamadas de método ocorreram dentro do esperado."

06 · CÓDIGO JMOCKIT

Exemplo Prático: Mocking de Dependências

@RunWith(JMockit.class)
public class PedidoServicoTest {

    @Tested private PedidoServico servico; // Classe sob teste
    @Injectable private PagamentoGateway mockGateway; // Dependência mockada

    @Test
    public void deveProcessarPagamentoComSucesso() {
        // 1. RECORD PHASE
        new Expectations() {{
            mockGateway.autorizar(anyBigDecimal); result = true;
        }};

        // 2. REPLAY PHASE
        boolean sucesso = servico.finalizarCompra(new BigDecimal("150.00"));
        assertTrue(sucesso);

        // 3. VERIFY PHASE
        new Verifications() {{
            mockGateway.autorizar(withEqual(new BigDecimal("150.00"))); times = 1;
        }};
    }
}
🎙️ O que falar: "Observando o código Java puro com JMockit: usamos @Tested para a classe principal e @Injectable para a dependência. As expectativas e verificações utilizam blocos de inicialização anônimos."

07 · MATRIZ COMPARATIVA

Comparativo Técnico Detalhado

Critério Spock Framework JMockit
Mecanismo Interno AST Transformations do Groovy em tempo de compilação Redefinição de Bytecode via Java Instrumentation Agent
Legibilidade e Expressividade Altíssima (Nomes de testes em strings, blocos BDD) Média (Estrutura rígida de classes internas anônimas)
Mock de Estáticos / Privados Limitado (Prioriza código bem desenhado / refatorado) Total (Mocka construtores, estáticos e métodos privados)
Testes Parametrizados Nativo e intuitivo via tabelas de dados (where:) Depende dos recursos do JUnit (ex: @ParameterizedTest)
Ecosistema e Ferramentas Integração nativa com Gradle, Maven, IntelliJ e Eclipse Requer configuração de agente JVM (ex: `-javaagent`) nas versões recentes do Java
🎙️ O que falar: "Esta tabela consolida as diferenças: o Spock aposta em legibilidade e AST Transformations do Groovy, enquanto o JMockit aposta em manipulação direta de bytecode para mockar estruturas complexas em Java."

08 · ANÁLISE CRÍTICA

Prós, Contras e Mitos das Ferramentas

Spock Framework

Vantagens: Relatórios detalhados contendo os valores de cada variável em falhas de asserção. Excelente produtividade para cenários complexos.

Desvantagens: Necessidade de compilar código Groovy no pipeline de build; resistência de times puristas em Java.

JMockit

Vantagens: Não exige linguagens adicionais no projeto. Capaz de testar sistemas legados sem necessidade de grande refatoração prévia.

Desvantagens: A capacidade de mockar tudo pode incentivar maus ambientes de arquitetura (código fortemente acoplado).

🎙️ O que falar: "Analisando criticamente: o Spock nos dá relatórios fantásticos sobre o motivo exato da falha. O JMockit é uma ferramenta poderosa para sistemas legados, mas exige cuidado para não mascarar problemas de design do código."

09 · RECOMENDAÇÕES E CONCLUSÃO

Diretrizes de Tomada de Decisão

Adote o Spock Framework quando: O projeto busca uma cultura forte de testes BDD, especificações vivas lidas por analistas ou desenvolvedores, e existe abertura para utilizar Groovy na camada de testes da aplicação.

Adote o JMockit quando: O projeto possui restrições estritas para o uso exclusivo da linguagem Java e requer simulação avançada de classes legadas sem alterar os fontes originais.

🎙️ O que falar: "Para concluir nosso trabalho: ambas as ferramentas entregam grande valor. A escolha dependerá da arquitetura do projeto e do perfil do time. Muito obrigado a todos pela atenção e ficamos abertos a dúvidas!"
